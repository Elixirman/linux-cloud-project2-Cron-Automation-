Cron Job Automation

Turning a script that runs correctly by hand into one that runs correctly unattended — the exact distinction that separates a personal utility from a production system.

Crontab Scheduling Unattended Execution Logging

1. Overview

Project 1 produced a script that performs a backup correctly when a human types the command and watches the output. That is a meaningful first step, but it is not yet automation — it still depends on someone remembering to run it, every night, indefinitely. A script that requires a human to remain reliable is not more trustworthy than the human's memory.

This project removes that dependency using cron, the Linux daemon responsible for running commands on a fixed schedule without any user present. The mechanical part — writing a line into a crontab — takes a few minutes. The harder and more instructive part is that cron does not run a script the way an interactive shell does, and a script written only for interactive use will frequently fail the first time it runs unattended, often silently. This project is as much about that gap as it is about the scheduling syntax itself.

2. From Manual to Unattended

The backup script from Project 1 was invoked directly: ./backup.sh, typed in a terminal, in a specific directory, by a specific logged-in user, with that user's full shell environment available. Cron changes every one of those conditions at once. A cron job runs:

  • with no controlling terminal, so nothing printed to standard output is visible unless explicitly redirected
  • with a minimal environment — most of the shell variables an interactive session takes for granted are simply not set
  • from an unspecified working directory, which should never be assumed to be the script's own folder or the user's home directory
  • on a fixed schedule, with no opportunity for the script to ask a question or wait for input

None of this is a defect in cron. It is cron behaving exactly as an unattended scheduler should. The obligation falls on the script: it must not depend on any assumption that only holds true in an interactive session.

3. The Environment Problem

The Project 1 script located its backup destination with BACKUP_DIR="$HOME/backups". This works reliably when a logged-in user runs the script, because $HOME is part of that user's shell environment. Under cron, environment variables are not guaranteed to carry the same values — and more importantly, tying the backup location to $HOME at all was already the wrong design decision, independent of cron: it meant the script's output location depended on who ran it and from where, rather than being a fixed, predictable property of the script itself.

The general principle: a script intended to run unattended should never depend on the current working directory, an inherited environment variable, or any other piece of context that only exists because a human happened to be present when it started. Everything it needs should be derived from something stable — in this case, the script's own location on disk.

4. Making the Script Self-Locating

The fix replaces $HOME with a path computed from the script's own file location, using the shell's special positional parameter $0 — which always holds the path the script was invoked with, whether that invocation came from an interactive shell, an absolute path, or cron.

#!/bin/bash SOURCE_DIR="/var/www/html" SCRIPT_DIR="$(cd "$(dirname "$0")" && pwd)" BACKUP_DIR="${SCRIPT_DIR}/backups" TIMESTAMP=$(date +"%Y-%m-%d_%H-%M-%S") BACKUP_FILE="${BACKUP_DIR}/backup_${TIMESTAMP}.tar.gz" if [ ! -d "$SOURCE_DIR" ]; then echo "ERROR: Source directory '$SOURCE_DIR' does not exist." exit 1 fi mkdir -p "$BACKUP_DIR" echo "Starting backup of '$SOURCE_DIR'..." tar -czf "$BACKUP_FILE" -C "$(dirname "$SOURCE_DIR")" "$(basename "$SOURCE_DIR")" if [ $? -eq 0 ]; then echo "SUCCESS: Backup created at '$BACKUP_FILE'" exit 0 else echo "ERROR: Backup failed." exit 1 fi

dirname "$0" extracts the directory portion of the script's invocation path; wrapping it in cd ... && pwd converts that into a clean absolute path regardless of whether the script was called with a relative path, an absolute path, or through a symlink. The result, SCRIPT_DIR, is then used to build BACKUP_DIR — so the archive always lands inside the project's own backups/ folder, no matter who runs the script, from where, or under what scheduler.

This is a small change in line count and a significant change in reliability. It is also the single most common defect in scripts that "worked when I tested them" and then failed the first time cron ran them.

5. Writing the Crontab Entry

Each user on a Linux system has a personal crontab, edited with crontab -e and never edited as a plain file on disk directly. The entry added for this project:

0 2 * * * /home/linux-guy/linux-project2/backup.sh >> /home/linux-guy/linux-project2/backups/backup.log 2>&1

Two details matter beyond the schedule itself. First, the path to the script is absolute — ~ and relative paths are not reliably expanded in a crontab and should never be used there. Second, the redirection: cron does not display a script's output anywhere a human will see it by default (historically it is mailed to the user via the system's mail transport, which is frequently unconfigured). Explicitly appending both standard output and standard error to a log file — >> ... 2>&1 — is what turns an invisible unattended run into one with a durable, inspectable record.

6. Crontab Syntax

A crontab line has five time fields, followed by the command to run:

MinuteHourDay of MonthMonthDay of WeekCommand
02***/home/linux-guy/linux-project2/backup.sh >> .../backup.log 2>&1

Each field accepts a specific value, a range, a step, a comma-separated list, or * to mean "every value in this field." 0 2 * * * reads as: minute 0, of hour 2, every day of the month, every month, every day of the week — in plain terms, every day at 02:00. Because the day-of-month and day-of-week fields are both *, no additional constraint is placed on which days qualify; the job runs daily.

7. Testing Without Waiting

A schedule of "once a day at 2 AM" is not something a reasonable engineer verifies by waiting until 2 AM. The standard practice is to add a second, temporary crontab entry timed a few minutes in the future, confirm it fires correctly, then remove it — leaving only the intended schedule in place.

# Temporary — verifies execution a few minutes ahead, then removed 9 22 * * * /home/linux-guy/linux-project2/backup.sh >> /home/linux-guy/linux-project2/backups/backup.log 2>&1

This test entry ran at 22:09 on the day this project was built, with no manual invocation of the script, and produced a verified archive and a populated log — the evidence reproduced in Section 10. Once confirmed, the temporary line was deleted, leaving only the 02:00 schedule.

A near-term test is not a shortcut around proper verification — it exercises the exact same code path (cron invoking the script directly, with cron's environment, not a human's) that the real 2 AM run will use. The only thing it changes is how long you wait to find out whether it worked.

8. The .gitignore Precedence Lesson

An early version of this project's .gitignore, carried over from Project 1, opened with a broad rule intended to keep the repository free of stray editor and OS files:

.* !/.gitignore

This says: ignore every dotfile, then explicitly un-ignore .gitignore itself. It works, until a second dotfile needs to be tracked deliberately. A placeholder file — backups/.gitkeep, added specifically so an otherwise-empty directory would still exist in the repository — was silently caught by the same broad rule, and needed its own explicit exception (!backups/.gitkeep) before git would recognize it.

Rather than repeat that pattern in this project, the .gitignore was written the other way around: list exactly what should be excluded, and exclude nothing else by default.

# Generated backup artifacts — not source backups/*.tar.gz backups/backup.log # OS/editor cruft .DS_Store *.swp
The general lesson: .gitignore rules are evaluated top to bottom, and a broad early pattern silently governs everything that comes after it — including files added much later, for unrelated reasons, by someone who has forgotten the broad rule exists. An explicit allow-list of what to ignore is more verbose than a blanket pattern, but it fails predictably: a newly added file is tracked by default rather than mysteriously absent from git status.

9. Architecture

Figure 1. Cron wakes every minute, matches the schedule field, and invokes the script directly — bypassing the interactive shell environment shown, dashed, on the right, that the original script mistakenly relied on.

Reading the diagram

The dashed box on the right represents everything an interactive login shell provides that cron does not: an expanded $HOME, a full $PATH, a terminal to print to. The solid path down the left and center is what actually executes a scheduled job — the daemon matching the current minute against the crontab, invoking the script directly, with the script responsible for supplying its own context rather than inheriting it. The output branches into backup.log via explicit redirection, since nothing is captured otherwise.

10. Evidence of Execution

The temporary near-term test described in Section 7 produced the following, entirely without manual intervention:

$ date Wed Sep 16 22:12:11 WAT 2026 $ cat backups/backup.log Starting backup of '/var/www/html'... SUCCESS: Backup created at '/home/linux-guy/linux-project2/backups/backup_2026-09-16_22-09-04.tar.gz' $ ls -lh backups/ -rw-rw-r-- 1 linux-guy linux-guy 140 Sep 16 22:09 backup.log -rw-rw-r-- 1 linux-guy linux-guy 224 Sep 16 22:09 backup_2026-09-16_22-09-04.tar.gz

The timestamp inside the archive's filename (22-09-04) matches the scheduled minute, not the time this evidence was captured (22:12) — confirming the run was triggered by cron at the scheduled minute and not by a coincidental manual invocation shortly before.

12. Failure Modes Encountered

Backups written to the wrong location

The script's original $HOME-based path sent archives to a folder outside the project entirely. Fixed by deriving BACKUP_DIR from the script's own location instead of the caller's environment.

Executable bit not set after a heredoc write

A file written with cat >> file << EOF is not executable until chmod +x is run separately — and in some terminals, a multi-line heredoc pasted as one block can fail to execute cleanly at all, silently writing shell syntax into the file as literal text. Verified afterward with ls -la to confirm the permission bits and cat to confirm the file's actual contents.

History expansion on an unescaped !

An interactive Bash shell intercepts ! for history recall by default, even inside double quotes. A line meant to be written literally into a file (!backups/.gitkeep) instead triggered event not found. Resolved by writing the line through an editor rather than echo, which never interprets its argument as a history reference.

A broad .gitignore pattern catching an unrelated file

.*, intended to exclude OS and editor clutter, also silently excluded a deliberately created placeholder file (.gitkeep). See Section 8 for the fix and the general lesson.

13. Extension Exercises

1. Alert on failure

Extend the crontab entry, or the script itself, to send a notification — email, a webhook, a message to a monitoring endpoint — specifically when the exit code is nonzero, rather than requiring someone to read the log proactively.

2. Rotate the log file

An append-only backup.log grows indefinitely. Integrate it with logrotate, or add a size- or age-based truncation step, so the log itself does not become an unmanaged growth problem.

3. Add a systemd timer as an alternative

Implement the same nightly schedule using a systemd timer unit instead of cron, and compare the two: dependency ordering, logging via journalctl, and how failures are surfaced differ meaningfully between the two mechanisms.

4. Guard against overlapping runs

If a backup ever takes longer than expected, a second cron-triggered run could start before the first finishes. Add a lock file (or use flock) so the script refuses to run if a previous instance is still active.
